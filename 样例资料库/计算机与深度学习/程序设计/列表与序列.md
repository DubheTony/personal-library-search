# 列表与序列

程序经常需要同时处理一组同类数据。列表把多个元素按顺序放在一起，每个元素都有位置，可以依次读取、修改或删除。序列的顺序本身就是信息：排队顺序决定先处理谁，传感器记录中的位置代表先后时刻，任意调换元素都可能改变结果。

多数语言使用从 0 开始的下标。长度为 n 的列表中，第一个元素位于 0，最后一个位于 n-1。访问下标 n 会越界，因为它已经落在列表的有效范围之外。循环遍历时，需要把循环条件与长度对应起来；初学者常把“次数是 n”误写成“下标最大为 n”，于是多访问一个位置。

列表适合需要按位置读取的数据。通过下标访问通常很快，但在中间插入或删除元素，后面的数据可能需要整体移动。若程序经常在开头增删，链表、队列或其他结构可能更合适；若主要任务是按键快速查找，哈希表通常比从头扫描列表有效。选结构应从主要操作出发，而不是只看它能否保存数据。

列表可以容纳另一组列表，从而表达二维表格或网格。图像像素、棋盘位置和课程表都能按行列组织。访问某个位置时，需要同时检查行号和列号是否有效；若各行长度不同，不能假定每一行都有相同列数。二维结构让局部关系明确，但规模变大后也要考虑内存占用和遍历顺序。

遍历列表最直接的做法是从头到尾访问每个元素。若每次处理都要在列表中再查找另一个元素，整体工作量可能快速增加。例如，两层循环会检查许多元素对，数据量增大时耗时往往比单层循环增长更快。先理清每个循环的任务，再考虑是否能用索引或集合减少重复查找。

列表常被当作结果集合，却不应被当作所有问题的答案。排序、去重、查找和按优先级处理分别有自己的算法与数据结构。列表提供有序存储，具体用什么方法，还取决于数据量、是否允许重复、修改是否频繁以及结果是否必须稳定。把这些需求说清楚，才能选出容易维护的实现。

列表的边界还会影响接口设计。函数若接收列表，应明确它是否会原地修改、是否保留原顺序，以及空列表如何处理。调用者知道这些约定后，就能决定是否先复制数据，也能避免多个模块意外共享同一份可变状态。处理文件或检索结果时，按稳定规则遍历列表还能让显示顺序在多次运行间保持一致。
